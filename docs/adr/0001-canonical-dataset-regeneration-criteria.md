# 1. Canonical dataset regeneration acceptance criteria

Date: 2026-06-13

## Status

Accepted

## Context

The canonical match-results CSVs (`CompleteDS_CSV.csv` for PL, `CompleteDSChamp_CSV.csv`
for EFL) are gitignored build artefacts regenerated by a build script from cached
football-data.co.uk raw season files. They feed all model training.

When a new season needs to be added, the build script regenerates the *entire* CSV
from scratch — every historical row's computed features are recomputed, not just the
new season's. This raised a question during the EFL 2025/26 refresh (Task #8): the
live EFL canonical was generated on 2026-04-07 by a build-script version that was
never committed (the script was first committed 2026-04-27, twenty days later). We
therefore cannot diff against, or reproduce, the exact logic that built the live file.

A naïve "regeneration must produce byte-identical historical rows" gate is therefore
unachievable: if the build script's feature logic improved between the old generation
and now, historical computed-feature columns will legitimately differ.

## Decision

We split the canonical's columns into two classes with different guarantees:

- **Facts** (Date, Home_Team, Away_Team, Home_Goals, Away_Goals, TG, FTR, HT scores):
  copied verbatim from the cached raw season files. These **must be byte-identical**
  across a regeneration. A difference here indicates raw-cache corruption or a column-
  mapping change and is a **hard stop** — investigate before proceeding.

- **Computed features** (rolling form, promoted/derby flags, etc.): regenerated by the
  current build script. These **may differ** across a regeneration if the build logic
  has improved. A difference is acceptable provided it is **characterised and explained**
  (which columns, how many rows, magnitude) and signed off.

Additionally, the **row count for pre-existing seasons must be unchanged** (no historical
matches lost, duplicated, or shifted) — a hard gate.

Rationale for accepting feature drift: the models are retrained from scratch on the
regenerated canonical immediately after. Internal consistency — every row built by the
*same current* script — matters more than matching a superseded script version we can no
longer identify. Forcing a match to the old logic would mean betting on models trained by
code we cannot reproduce.

## Consequences

- Regeneration is safe to run whenever a season needs adding; historical results are
  protected (facts hard gate) while feature logic is free to evolve.
- A backup of the current canonical and model pickles must be taken before regeneration,
  because the artefacts are gitignored and git provides no rollback.
- Any canonical regeneration is paired with a retrain (a **Data Refresh**), and the new
  models pass a diagnostics checkpoint (AUC/Brier/calibration old-vs-new) before going live.
- This methodology applies to both leagues. The PL canonical is subject to the same
  criteria the next time it is regenerated.
