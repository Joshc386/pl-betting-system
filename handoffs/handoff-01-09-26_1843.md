## The calibration finding, and why it matters

The user asked how No/Under bets perform against Yes/Over. The answer took four
passes and reversed twice. **Read this before touching the detector.**

**Under/No is not worse than Over/Yes.** The apparent difference was two
artefacts stacked:

1. **Selection.** `db.log_predictions` stores a prediction only when
   `edge_pct > 0`. Conditioning on the model's own positive edge inflates its
   apparent confidence *whatever its true calibration* — the winner's curse.
   Measured walk-forward on the OOF caches:

   | sampling | n | gap |
   |---|---|---|
   | every game, both sides | 27,922 | **+0.00 pp** [-0.54, +0.56] |
   | positive edge only (what predictions logs) | 13,961 | **+4.29 pp** |
   | edge >= 2% (the gate minimum) | 9,775 | **+6.26 pp** |

   The model is unbiased across every game. It is the *sampling* that is biased,
   on both sides symmetrically.

2. **Construction.** The first walk-forward pass used `roi_validate`'s mean of
   calibrated base models and found +1.70 pp. Production runs a **stacker**.
   Refitted walk-forward, the historical gap is **-0.33 pp** — indistinguishable
   from zero. Season 23 was **-7.29 pp**, a *larger* gap than the live 2025/26
   reading of -6.76, in the same direction. So the live season is an ordinary
   bad-calibration season, not a regime change.

**Numbers the detector needs, all measured:**

- all-games baseline **0.00 pp**, 95% CI **±0.55** (n=27,922)
- seasonal spread **-7.29 to +5.71 pp**, sign flips routinely, sd ~3.7-5
- selected-sample gap **~+6.3 pp** — expected forever, never a fault condition

Reproduce with `scripts/validate_calibration_drift.py` (criteria pre-committed
in `4f2aa1e`, before the measurement ran).

## The detector — design settled, not built

**Statistic:** all-games calibration gap — mean model P(side) minus realised
rate — over settled `match_analysis` rows, rolling.

**Why `match_analysis`:** it is the only unbiased sample, and it only became one
this session. `0c63d7d` added `settled` / `won` / `actual_result` / `settled_at`
and `settlement.settle_match_analysis()`, wired into `scheduler.job_settle_bets`.

**Detection is necessarily slow** — this is the constraint that shapes the whole
thing:

| window | n | 95% half-width |
|---|---|---|
| one matchday (PL) | 60 | ±12.65 pp |
| one week, both leagues | 108 | ±9.43 pp |
| one month | 432 | ±4.72 pp |
| one full season | 2,796 | ±1.85 pp |

Against a natural seasonal swing of 13 pp. **A weekly alarm is mathematically
impossible** — one week's interval is wider than the entire historical range.
Useful detection starts at a month. This is a health check, not an alert.

**Firing rule:** the rolling gap's confidence interval must exclude the
historical seasonal range, not merely be non-zero. Six seasons is a thin
reference and the surface should say so rather than imply precision it lacks.

**Must never:** fire on the selected sample, fire weekly, fire inside ±5 pp, or
adjust anything. It reports; the user decides.

**Where:** a band and status line on the existing Calibration chart (`fig_cal`,
`dashboard.py`), not a new tab.

**Data reality on day one:** EFL settled 160/160; PL only 60/352, because the
rest predate ESPN's window. The PL series fills forward from here, so the
detector will be data-starved on the PL side for a while and should say so
rather than render a confident empty band.

## The Match Centre filter — decided, not built

Grilled to completion. `_build_match_centre` currently shows ~71% of rows when
~19% (PL) / ~13% (EFL) are recommended — about four rows read per actionable
bet.

| Decision | Answer |
|---|---|
| What survives | Rows where the **gate's edge > 0**, which is exactly the recommendation set |
| Alt-line `✓ DC` rows | **Kept**, visually distinct. Excluding them would make the display adjudicate strategy |
| Which numbers show | The recommendation's own (`edge`, `blended_prob`, `ev`, `stake_pct`) |
| Rejected rows | Behind the existing `Show all markets` toggle |
| Empty state | States the age of the odds **in the same sentence as the verdict**; no new staleness constant |

**Why the gate's edge and not the displayed one** — this is the load-bearing
finding and it is not written down anywhere else. The displayed `Edge %` is
`model_prob - fair_prob`; the gate decides on `blended_p`. Across 56 recommended
PL rows the displayed number averages **2.5x** the gate's (7.43% vs 3.02%), and
one recommended `btts/no` row displays **-0.631%** while the gate saw +1.7% with
`n_agree = 4`. **Filtering on displayed edge would hide a four-model
recommendation and keep 118 unrecommended rows.**

`freshness.py` does **not** measure odds staleness — it reconciles the canonical
against finished fixtures. There is no existing odds-staleness threshold to
reuse; that is why the empty state states the age instead of judging it.

## Lessons that cost time this session

- **Ask which rows an analysis is looking at, before interpreting it.** Three
  analyses this session used three different populations — every game, positive
  edge only, gate-passed — and conflating them produced a finding that reversed
  once separated. This was the single biggest time sink and the most valuable
  correction.
- **Check the measuring instrument matches production.** `roi_validate` averages
  base models; production uses a stacker. Measuring with the wrong one turned a
  clean record into a +1.70 pp bias and an ordinary season into a regime change.
- **A test can be vacuous in more than one way.** Writing one behavioural test
  produced two vacuous passes in five minutes — a frame where cohort and actual
  carried the same value, then a frame where the arrival was present in both
  seasons, which the PL detects via a flag and the EFL does not detect at all.
- **`ls`/`grep -r` from the project root still times out.** Cost one killed
  background task again. Use the Grep and Glob tools.
- **Screenshots do not work in this session type** — the Browser pane is not
  displayed, so pages do not composite. `read_page`, `get_page_text` and
  `javascript_tool` all work, and DOM inspection was enough to verify the chart
  restyle.
- **Check the date from the clock.** Corrected once already in the last block
  and nearly repeated.
