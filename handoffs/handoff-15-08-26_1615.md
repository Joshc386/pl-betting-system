### 1. Job-freshness strip (dashboard, top of page)

`job_health.py` + `_make_job_status()` in `dashboard.py`. Renders:

```
Jobs: Ingest 3h ✓ · Settle 3h ✓ · Retrain 5.2d ✓ │ Backlog 0 │ Data PL S25 · EFL S25
```

Exists because **ADR 0006's catch-up failed silently on 14 August** and nothing noticed
— `LastTaskResult` and `NumberOfMissedRuns` both still read `0`, because the last run
that *happened* succeeded. `logs/daily_settle_20260814.log` is simply absent. See the
counterexample already recorded in `docs/adr/0006-task-scheduler-for-data-critical-jobs.md`.

Design points worth not re-deriving:
- Reads each job's **own log** (mtime + `exit=` line), never the data. "Ingest ran and
  upstream had nothing new" and "ingest never ran" are indistinguishable from data
  alone, and the first is the correct state every day until football-data.co.uk
  publishes 2026/27.
- Global, not league-scoped — one ingest and one settlement cover both leagues.
- Backlog threshold is **3 days**, because `scheduler.py:376` and `:384` pass
  `days_back=3`, overriding `settlement.py`'s own default of 7. Rows older than that
  are unreachable by any scheduled run.
- **Known limit:** infers "did it run" from log age, so a missed daily job only trips
  amber past 36h. On 14 Aug it would have shown amber from ~20:00, green at lunchtime.
  The precise alternative ("should have run by 06:00 + grace") was scoped and not
  built.

### 2. REC column shows model agreement (was a bare tick)

Per the user's spec: **agreeing / all available models** — 4 PL, 3 EFL. A Dixon-Coles-only
alt line reads `1/3`, not `1/1`.

Implemented by adding a `league` argument to the existing `_model_agreement` in
`dashboard.py` (the 16:11 session's function) rather than writing a second copy.
`ENSEMBLE_SIZE` lives in `staking.py` and is imported, so the denominator cannot drift
from what each league trains. The analytics caller omits `league` and keeps its existing
behaviour exactly, including returning `"DC"` for alt lines.

REC degrades to the old `✓` when the breakdown is unknown, which is what it is doing
right now — see "Next session".

### 3. The bug behind the empty AGREE column

`match_analysis.per_model_json` was `"{}"` on every row, which is why AGREE read `—` on
all 49 lines while `recommendations` held full breakdowns. Two causes, both fixed:

1. `scan.py`'s rebuild wrote `per_model_probs = {}` over the predictor's good rows —
   `save_match_analysis` deletes and re-inserts per fixture, so the later write won.
2. `db.py`'s carry-forward would have rescued it but was gated behind `if model_p is
   None`, and the rebuild always supplies `model_prob`, so it never fired.

Fixes: carry-forward now runs on its own terms (`db.py`), and the rebuild passes the
recommendation's breakdown through directly via `_rec_per_model()` (`scan.py`) rather
than depending on write ordering.

### 4. Trap documented while testing

**Alt lines and ensemble markets store different things under `per_model_probs`.**
`predict.py:1383` writes `{"dc_poisson": vb["model_prob"]}` where the value is already
the probability *for that row's side*; ensemble markets store Over-probabilities and
derive Under as `1 - v`. Applying the ensemble's inversion to an alt line reports the
opposite of what the model said. Covered by `test_alt_line_under_is_not_inverted`.

### 5. Three test rows deleted

`predictions` ids 137/138/139 (PL) — Arsenal v Chelsea ×2, Liverpool v Man Utd, all
kickoff 2026-04-12, all `created_at` three weeks *after* kickoff, all carrying identical
placeholder values (`model_prob=0.62`, `best_odds=1.95`, Pinnacle) across two different
markets. User confirmed test data. Deleted by the user by hand — the auto-mode
guardrail correctly blocks agent DB writes.

Backup: `data/dashboard.db.bak-20260815-prephase1`. Unsettled backlog is now a **true
zero**, so any future non-zero is real.
