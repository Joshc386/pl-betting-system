## What was actually wrong — three faults, diagnosed separately

The user reported "most fixtures show nothing" and it turned out to be three
unrelated causes. Worth knowing, because two were invisible and one was mine.

1. **Cross-league odds race** (`688c8ba`). `api.odds_api.SPORT` and `CACHE_FILE`
   were mutable module globals swapped in place by request-scoped callers, on a
   threaded Flask server (`app.run(debug=False)` leaves `threaded=True`). Two
   league tabs scanning concurrently crossed the caches: 24 Championship
   fixtures in the PL cache, 20 PL fixtures in the EFL cache. **The EFL produced
   zero recommendations for over a week and nothing raised** — mapping failures
   logged individually at INFO, and "Generated 0 Championship recommendations"
   reads the same as a quiet week. Now parameters, no shared mutable state.

2. **Contamination residue** (`3336119`). The race fix stopped the bleeding but
   could not clean it: `save_match_analysis` only deletes rows for fixtures the
   current scan covers, so 40 foreign rows in the EFL database were immortal and
   rendered as blank Match Centre rows. Purged on `scanned_at`, **not** team
   name — three of the ten contaminated fixtures have both teams in the EFL's
   historical canonical, so a name filter would have left them behind.

3. **The season bump, for the second time** (`3336119`). `E0` 2026/27 published
   between 30 Aug and 1 Sep (HTTP 300 → 200; verified against the `Div` column,
   not the status code, because this host serves a different division under 200
   rather than 404ing). But `build_canonical_dataset` reads
   `current_season_idx` as `last_season`, so while it said 25 the rebuild could
   not fetch season 26 **even after upstream published**. The gate's "missing 19
   finished fixtures" reads as an upstream problem and hides the local half
   completely. **This is the identical trap the EFL hit eleven days earlier**,
   and it cost the PL the whole opening month.

## Lessons that cost time this session

- **A fix can be correct and the symptom persist.** The race fix was right and
  the dashboard still looked broken, for two further reasons. Re-check the
  observable after every fix rather than reasoning that it must now be better.
- **A long-running dashboard holds stale code.** The user was testing against a
  process started before the fix. Any "did the fix work" check needs a restart
  first.
- **Verify a 200 against the payload, not the status code.** `E0` answering 200
  is not proof it published; the `Div` column is.
- **Two of my own diagnostic probes were wrong before one was right** — one
  reimplemented the code under test instead of calling it, the other measured
  final file state and so missed a write that was later overwritten (0/40 clean
  when the bug fired every time). Recording each write as it happened took it
  to 9/9.
- **Check what a name-based filter would catch before deleting on it.** Three of
  ten contaminated fixtures had both teams in the EFL's historical canonical.
- **Quote heredocs that write Markdown** (`<<'PY'`). An unquoted one executed
  every backtick in the text and stripped inline code spans from the vault's
  `progress.md`; caught and repaired the same minute.
- **Background tasks lose piped stdout, and a killed process writes no `EXIT=`
  marker.** Redirect to a file, and treat a missing marker as "killed", not
  "clean".
